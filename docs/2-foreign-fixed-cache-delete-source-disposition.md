# Legacy-name cleanup does not check who made the cache

When the worker activates, it deletes caches named tetris and tetris-2 without checking their creator. A cache under either name can belong to another same-origin project. Under that declared foreign-creator premise, successful activation deletion conflicts with APP6's instruction to delete only caches the game made.

Candidate conditional source disposition for independent review. Not a new execution, recovered V47 raw result, universal namespace theorem, production correction or phase exit. Existing NEW362 failure/delete-reopen finding concerns a different trigger and backing identity.

## Criterion and admission

APP6 says projects share origin caches and the game deletes only caches it made. Blueprint4.8 explicitly admits a cache from another project using a name the worker deletes, including tetris and tetris-2; it says apparent conflict must receive Candidate/disposition analysis, not that those names imply game ownership. D24V1 trusts successful browser cache semantics, not the project's creator inference or cleanup policy.

Choose one same-origin foreign project's cache under name tetris, created by that other project before this worker activation. Its creation and retained ownership are declared independent facts, not inferred from name. It contains any one response with no game claim; content compatibility is immaterial to the deletion rule. The game has not created, opened, taken over, replaced or overwritten that binding. The tetris-2 name is absent, no concurrent actor changes either name, and every selected API succeeds according to its contract. This is a specified foreign-name attack input, not proof of physical historical occurrence.
