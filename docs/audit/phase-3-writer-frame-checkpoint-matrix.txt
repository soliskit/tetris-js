# Phase 3 writer, frame and checkpoint matrix: candidate-stage limits and gaps

This record was rewritten in place on October 25, 2026 from the longer matrix paper of the same name (prepared October 5, 2026), which is in git history. The paper mapped 35 state writers (W01 to W35) in the game code to the allowed state changes and the checks that cover them. Every row is marked "Candidate mapping; Not Assessed" for the implementation, frame and checkpoint claims. This record keeps the stated limits, the open gaps and the entry-wrapper rows the closure record cites (W03 to W05, close to the paper's text). For the other 32 writer rows it keeps one line each of the paper's observed checkpoint placement and what remained to be established, condensed for this rewrite. For the 21 source-side operation rows it keeps the frame rule and the limits and open statements, also condensed for this rewrite. It is dated candidate-stage text, not shown to be the limits behind any certification word. The original was written in compressed shorthand with run-together words; the text below is re-spaced and lightly reworded for readability on October 25, 2026, with the same meaning intended. The original is this file's earlier version in git history; the last commit containing it is the parent of the rewriting commit, which the decision row names with the file's SHA-256. Decision identifiers such as D16 or D32 are rows of `docs/decisions.md`; codes such as V1, F2, R1 B1, S9, T3, U3, U4, Z1, C1 to C4 and E1 to E3 are items of those decisions and of the Phase 1 record files in `docs/audit`; SAF-4 and INP-3 are requirement IDs in `docs/requirements.md`. Line numbers below are as of the paper's base, which it does not name by commit, and may not match today's files.

Provenance as stated in the paper. The base was a pinned checkout whose public, test and config bytes it calls "equal" (the paper does not say equal to what) and names no commit. Its sources were the exact D16, D17, D18, D20, D21, D22, D23 and D31 to D34 statements, the decision index and ledger status, the Phase 2 integrated record and inventory papers P2-A to P2-D, and the then-current references in the game manager, input controller, script, Tetromino, factory, game state, position and session code. A documentation pull request (PR 77 of the project repository) was pending and was not treated as governing text. The paper did no repository, permanent-test, model-author or contact work, no execution, no findings promotion and no phase closure. Existing tests were searched as leads only; none was run for the matrix. No model relation was authored. Expected meaning was derived from the requirements and adopted decisions, not from the production monitor.

What the paper covers, and what it does not prove. It is a static ledger of route families and writers for the scoped production base. Completeness is not machine-checked, including aliases and in-place writes. It is not a proved frame matrix for all reachable states. Helper functions may run inside larger legal operations, and field assignments are not necessarily separate commits. An outer authoritative write is not covered merely because an inner game-manager action is guarded. There is no runtime or syntax-tree exhaustiveness check, no alias proof and no fault trace at a checkpoint.

Where the per-row content lives now. The 35 production-route anchors and the 35 per-row evidence gaps are held, with identical text, in `docs/audit/2-phase-4-writer-route-index.json`. Each writer row's specified rule and concrete writes (not in that file, except the observed absences kept in the row lines) and the state-item assignments of the 21 source-side operation rows L01 to L21 are not carried over and are in git history only; the limits and open statements of those rows are kept below. The three rows the closure record's Entry-wrapper entry cites (W03, W04, W05) are carried below.

### Items the rows track (legend)

A1 locked board. A2 falling piece. A3 held piece. A4 hold used. A5 next three pieces. A6 piece bag. A7 score. A8 mode. A9 reset count. A10 confirmation pending. A11 selected choice. A12 physically held input tokens and newest order. A13 repeat position. A14 touch drag. A15 greatest occupied row ever. A16 session withdrawn indicator. GM is `public/game/gameManager.js`, IC is `inputController.js` and SC is `public/script.js`, as in the paper.

Stated reading rules. In an ordinary game over, A2, A3, A4, A6, A9, A14 and A15 have no semantic value, and the paper says clearing them is not mandatory. A5 keeps a valid queue. A11 is absent unless a confirmation is pending. Runtime handles and resources are not identical to the A13 phase. Storage eligibility, score and payload are persisted, but the paper does not treat them as authority for A16 or A7 by name. No implicit exception is granted.

### Normative baseline the paper used

The conceptual commit in D16 is independent of guard names. V1 makes validity commit-only. F2 keeps ordinary contents after a fault, plus the mandated safe effects. D31 Z1 says every operation changes only its assigned items; the D32 operation table, D33 C1 to C4 and D34 E1 to E3 govern the assignments. SAF-4 is literal: every action and every timer. D23 U4 includes gravity, lock and repeat, and excludes draw and poll, but downstream authority is not excluded. A successful cancel means no fire (D22 T3). A failed cancel may fire but must not mutate a stopped game (D23 U3). D18 B13 defines running as an outstanding firing, not a non-null handle. The constructor's opening state is valid separately under R1 B1 and is not an ordinary runtime action. Presentation focus can represent A11, but trust in native browser behavior does not prove the project's mapping. A16's lifetime (D20, D21 S9) is true from a withdraw or attempt and clears on session start or this session's successful save; external writes never clear it.

### Checkpoint coverage summary

For game-manager actions, the guard runs the whole action inside a checked closure, then the invariant check runs, and a throw or violation goes to the safe-failure path. The monitor reads board shape, queue count, score as an integer and multiple of 100, the playing piece's fit, the manager's gravity and lock handles, and resting state. It does not check the whole of R1, control or repeat state. The change callback is outside the catch. For game-manager timers, the schedule wraps the whole callback guard, including a null gravity handle and the drop, lock and spawn work; a late failed-cancel callback still enters. Direct helpers have no checkpoint. Input-controller control and repeat writes have none for their own authoritative writes; some inner gameplay calls have game-manager checks, the repeat-stop branches have none, and set and clear happen outside the game-manager fault catch. Script touch and focus writes have none for their own authority; some inner calls have checks, and the render catch is recovery, not a semantic invariant or fault-terminal checkpoint. The constructor has none. Persistence has no check of its own postcondition; some effects happen inside the outer closure before its post-check. None of these independently proves frame, or the fault, resource and report criterion.

### Other writer rows: observed checkpoint placement and what remains to be established

These are the notes the paper recorded for the 32 writer rows other than W03 to W05, one line each: where a check was or was not observed (with the few absences the paper noted in the row's writes), and what the paper said still has to be established. Each row's anchor and evidence gap (held in the route index) are not repeated. Writer lines are as of the paper's base.

- W01 (opening and constructor). Placement: No guard, runChecked or monitor at construction; the factory's generate or spawn may throw before the opening is completed. There is no explicit A16 write. To establish: The opening needs a separate semantic initialization map; it is not a fictitious legal operation and does not require clearing absent fields. Controller, drag and focus are constructed later.
- W02 (initial held controls and polling). Placement: No engine checkpoint; initial polling is scheduled (lines 94 and 99 to 112). To establish: A semantic projection of the initial held controls and repeat is required; the polling runtime marker is not A13.
- W06 (New Game). Placement: One game-manager monitor runs after the whole operation; intermediate paused or playing resource states inside it are allowed under V1; the storage effect has a precheck. The code has no explicit A12, A13 or A14 reset. To establish: The authoritative model assignment must cover the nested reset, spawn and withdraw. A12, A13 and A14 effects are not automatically authorized wholesale by New Game; the actual D32, B12 and partial choices apply.
- W07 (Continue). Placement: One game-manager monitor runs after the return when the call came through handleAction; a direct call has none. To establish: Restoration differs normatively from a new-piece reset for Continue; rejecting a whole withdraw (S7, S11 semantics) is separate. A10 is cleared by the dispatcher and is not listed in the Continue restore.
- W08 (pause and page hidden). Placement: The game-manager monitor after the pause checks game-manager handles only; there is no input-controller repeat checkpoint; the page-hidden A14 reset happens outside it. To establish: A page-hidden A14 clear must map to composite touch-cancel operation 9 or an approved assignment, not automatically to the pause frame. A12 retention and the A13 idle and resume rule are distinct.
- W09 (resume). Placement: The game-manager monitor runs after the operation and does not cover input-controller state. The code has no input-controller suppression write or callback. To establish: Nested lock effects are authorized only under the specific B9.2 case; the representation of retained A12 and resume suppression is left open and is not fixed by handle naming.
- W10 (move). Placement: A guard applies when the call comes through an action; a direct public call has no monitor or change callback. To establish: Nothing changes if nothing fits; the lowest row is semantically the greatest occupied row, not the box row; a new lowest row resets the count and must not then increment it.
- W11 (rotate). Placement: The guard applies via the action; two in-place writes happen before the operation check; direct Tetromino or game-manager methods have none. To establish: A2 is valid at the conceptual commit and V1 allows internal steps; an unchanged rotation with a changed position needs classification if kicks allow the same orientation.
- W12 (gravity tick). Placement: The schedule (line 383) wraps the callback guard and the monitor runs after the full callback; a late gravity firing while over returns from the drop, but the monitor still runs. To establish: Timer handle bookkeeping is runtime, not A state; a successful cancel is assumed not to fire; a failed cancel must not mutate.
- W13 (soft drop from controls or gestures). Placement: The inner game-manager guard applies; the input-controller interval and script gesture outer writes are not covered by the inner check. To establish: One input event may comprise control progression, a soft drop and a touch counter; each needs a legal commit map.
- W14 (hard drop). Placement: The guard applies via an action only; a direct hard drop has none. To establish: The ghost getter (lines 353 to 356) mutates a copy only and is not an A2 writer until line 542; intermediate positions are not separate commits (V1).
- W15 (lock). Placement: The game-manager monitor runs after the timer body; a late callback after a failed cancel lacks an entry mode check before board writes. To establish: A late callback fired despite a cancel (U3) must not change a stopped state; existing guard checks after the writes cannot alone prove non-mutation.
- W16 (lock outcome and turn end). Placement: Only the whole outer action or timer is covered; a direct helper has none; the high score and save are written before the outer monitor. To establish: A3 is preserved at an ordinary lock; preserving and stopping A12 and A13 at over needs a cross-layer treatment; A14 can retain the old piece pointer while controls is false via identity, and that projection is not automatic.
- W17 (hold). Placement: The guard applies via handleAction; a direct hold has none. The no-room hold branch (mode line 567, flag line 568) returns before the held piece is assigned. To establish: Retained held and hold-used values at over are not alone invalid, because they are absent; a new queue-based hold may update the concrete held piece after over, and a projection is still required.
- W18 (spawn and new-current helpers). Placement: Only the outer guard covers them; direct helpers have none. To establish: These helpers are not independent authorized operations just because they mutate; there is no authority to set a new lowest row from a constructor's absent value.
- W19 (fault stop). Placement: It is called outside the operation's try, after a caught throw; throws from stopGameLoop and cancelLockDelay are not caught by failSafe; the reporting catch covers only push and onFault. The code has no input-controller repeat stop, A16 withdraw or persist write on this path. To establish: A fault is not an ordinary R1 state, so malformed-board validity or rollback cannot be demanded; the required safe changes are distinct from ordinary game over.
- W20 (persistence cache and save). Placement: No checkpoint for the setter or the read cache; a save inside a game-manager action is checked later; a direct save has none. There is no distinct A16 field writer. To establish: storedIsSessionSaved is an external flag cache, not automatically A16: storageChanged clears it and it re-reads an external true. Persistence operations may change things outside authoritative state without accepting a payload.
- W21 (external storage event). Placement: The game-manager outer check runs on some false calls; the storage event has none, because it touches only cache and presentation. To establish: An external flag write event is not a legal authoritative A16 change; no direct A16 assignment was found in the shipped source.
- W22 (dialog presentation). Placement: drawSafely (line 337) catches syncControls errors, not an R1, frame or engine-fault check; the initial context and RAF are separate. There is no separate A11 field. To establish: Dialog presentation has an authoritative selection dependency and is not excluded wholesale; pending true before RAF or native focus may temporarily lack a choice outside an unfinished game-manager operation.
- W23 (focus after the dialog changes). Placement: No engine check after the focus; only native focus and the render catch apply; a button click's game-manager guard checks A10 and game effects, not the focus domain. To establish: A11 is defined by the semantic projection of DOM focus while pending; native Tab, pointer, assistive-technology and browser focus are also writers outside the explicit focus callback.
- W24 (native focus and selection). Placement: There is no registered engine invariant check or native-focus admission; it does not go through a game-manager operation. To establish: Browser activeElement is trusted semantics (D27), not a projection mapping; outside a pending focus it is not an A11 writer, by semantic absence.
- W25 (held-token set). Placement: No check after the held-set write; the inner game-manager check runs only if a game action executed; dialog, unhandled and release paths may never check. To establish: The A12 physical-control domain cannot identity-map an aliased set; set order is available but resume uses a fixed A and D priority, not order; non-game keys may be runtime-ignored data, not authoritative tokens.
- W26 (repeat poll). Placement: The outer RAF poll's try catches to the console only, with no authoritative post-check of its own writes; nested game-manager actions check the game before later pad writes. To establish: Multiple physical sources in the same direction or priority must map to B12 as separate tokens with order; heldButtons is also an action-edge runtime cache, not necessarily all of A12.
- W27 (repeat start). Placement: The A13 movement write and the scheduler pre-clear are outside the game-manager guard; the inner check runs before the timer assignment or reissue; the stop branch (line 264) returns without a game-manager check. To establish: The semantic phase (waiting or repeating) is not an explicit field and is derived from timer history, not from a non-null movement or the handle alone; an equal-action early return (line 258) preserves the old phase.
- W28 (blur and disconnect). Placement: No game-manager check; a clear failure can prevent later clears; the blur and disconnect callback has no local catch. To establish: The fate of blur tokens is partial against the D32 release operation; disconnect releases all (INP4 as specified); the authoritative A12 and A13 runtime effects need a separate map.
- W29 (soft-drop repeat start and stop). Placement: No engine check on start, stop or after the callback returns; only the inner game-manager soft drop checks gameplay, after the pre-clear. To establish: The soft-token set projection needs the physical S, Down, stick and dpad inputs; the timer's semantic running is distinct from undefined and null.
- W30 (touch begin). Placement: No engine guard, check or catch; setCapture may throw after the A14 writes. There is no mode check. To establish: Start anchors may be retained when inactive and a projection is allowed; the concrete current Tetromino at over is not the semantic current; the pointer resource id is not necessarily all of A14's authority.
- W31 (touch update). Placement: Each game-manager move or drop guard checks before the following A14 writes; the outer handler's mode, frame and B12 have no check; an early identity return (line 444) leaves the fields. No current point is stored explicitly except through the event and the anchors. To establish: A composite gesture may include several semantic moves; authoritative touch-progress updates are not covered by the game-manager board check; anchor mutation versus the fixed original start and excursion (B12, E1) is distinct.
- W32 (touch end and cancel). Placement: The inner game-manager rotation checks before the A14 reset; a non-tap end or cancel has no game-manager check; a throw after the rotate and before cleanup is possible via onChange. There is no explicit measurement of the end distance. To establish: Cleanup is authorized operation 9, with no undo of committed moves or drops (E1); an invalid intermediate touch after a rotate may need a combined commit explanation.
- W33 (hidden touch reset). Placement: The A14 reset happens before the game-manager guard; hidden while paused or over has no commit check. There is no explicit drag reset for new, hold or lock except the identity checks at lines 444 and 488. To establish: Semantic controls false may derive from pointer identity while the old gesture anchors are retained; A14 is absent at over; a coordinate property is needed and is not assumed.
- W34 (direct helpers and mutable objects). Placement: Direct helper and field writes have no check and no onChange; the mutable getters are not defensive. All game-manager helpers are public, Tetromino rotate and position fields are mutable, and the factory's bag array is reset by reference; the shipped script and input controller call only handleAction, softDrop, togglePause, cancel, storageChanged and getters (P2 integration). To establish: Availability to a caller is not proof that the shipped entry exploits it; an attacker controlling their own browser is excluded (an anti-cheating limit); a formal API route boundary is needed and no server trust is invented.
- W35 (non-authoritative and temporary writers). Placement: The writers use their own appropriate evidence method, with no forced R1 check; focus, poll and control downstream exceptions are retained. The rows are specification-side mapping, not runtime verification or independent clean-author inputs. For A16 the paper found only the semantic lifetime target in W01 and W20 to W21 and no identified direct counterpart; W35 holds the non-authoritative or temporary writers.

### Gaps the paper recorded (open at that stage), labelled matrix G1 to G10

These are the matrix's own list; P3-C has a separate G1 to G10.

- Matrix G1. A projection from the definitions to concrete objects is missing for A11 native focus; A12 physical aliases, stick and directional-pad tokens and their order; A13 waiting, repeating and idle; A14 original point, current point and excursion; A15 greatest occupied row; and A16 session lifetime. Complete adapters and relations are missing. Fields must not be identity-mapped by name.
- Matrix G2. Composite operation boundaries need a source-grounded relation for: a control press plus a game action; a gesture update with several moves or soft drops; dialog render focus after a game-manager pending commit; a visibility-driven touch cancel plus pause; and another action cancelling a confirmation. No async grace period or guard-only boundary is introduced.
- Matrix G3. Each D32 and Z1 operation needs frame assertions over all state, not only modified fields. The R1 ordinary and fault distinction and the game-over semantic absence stay; the concrete queue remains valid. Some helper writes are permissible only as nested authorized transitions, not as independent API operations.
- Matrix G4. Repeat timers are physically outstanding between pause or game over and the next poll or tick; the relation of immediate U4 stop to R1 B13 is unproved. Failures of cancel, write, registration, the change callback, native focus and capture need real cut points and independently observed effects. A successful-cancel assumption is not replaced by an arbitrary invalid scheduler.
- Matrix G5. No explicit A16 writer exists. A flag cache, invalidation or reread of an externally true value cannot serve S9's lifetime without an equivalence proof. All withdraw, attempt and successful-save paths were listed in rows W20 and W21 (their specified rule and concrete writes are history only); no new persistent format or mechanism was selected.
- Matrix G6. The ordinary monitor is not an R1 oracle; it makes only partial checks. The literal SAF-4 checkpoint scope, through input-owned writes and timer stop branches, needs analysis before declaring a failure or waiving checks. No automatic expansion of the requirement to every DOM event; the relation between legal operation and value must ground which action occurred.
- Matrix G7. Constructor and opening validity and source exceptions need separate evidence. The paper does not assert that the absence of a guard automatically violates SAF-4 on the opening; B1 opening validity needs proof independent of the runtime action monitor. No automatic clearing of semantically absent fields.
- Matrix G8. Direct public helpers and mutable object references are reachable by code, but no shipped script or input-controller caller uses most unguarded methods (per a cross-file pass). In-scope boundary, reachability and hostile-input test domains are needed; no claim of unhackability in a user-controlled browser, and no fictional encapsulation.
- Matrix G9. D32 had partial points settled by D33 and D34; other partial model choices are not determined by production. Blur and new-game held-token representation and input-mode composites need a careful source relation, not a borrowed resume suppression or a new owner decision by default. A possible INP-3 modified-key interpretation remains the D40 gap, not resolved here.
- Matrix G10. Independently designed frame, checkpoint and fault differential tests were pending with the coordinator: predeclared semantic partitions, modes, pending flags, physical tokens, touch points, the "14-15-16 count" (the paper's own shorthand; the counted item is not stated in the paper), legacy validity, withdraw failures and exception cut points. No permanent tests were added and no model-author feedback came from this exposed matrix. Candidate observations need reproduction against the governing requirement and a disposition; no status was promoted.

### Source-side operation rows: limits and open statements

The paper's 21 source-side operation rows (L01 to L21) assign, for each operation, the state items it changes (A1 to A16), the items left unchanged (F) and the writer rows it uses; those assignments are history only. The frame rule behind them is kept: F is the set A1 to A16 minus the assigned items, preserved under Z1 except semantic absence or default effects explicitly sourced; the rows are D32's literal assignments with D33 and D34 completions, not a whitelist derived from the implementation; nested operations add only their source-assigned effects; a valid snapshot is not itself permission for an operation. For 19 of the 21 rows (all except L03 and L19) the paper says a source-citation check was pending and the row's assignments must not be treated as independently verified. The assumptions, limits and open statements each row carries are kept below.

- L01 (confirmation opens): the relation between the pending game-manager state and deferred focus is unresolved.
- L02 (selection change): native focus and checkpoint mapping are open.
- L03 (confirmation answer, New Game): D32 states give up and reset of board, score, held, queue, bag and hold availability, withdraw A16, and clear A10 and A11; the new current piece, reset count, lowest row and mode consequences need a composite cited from B8, B9.2 and STA1 and are not free permission for all controls. Cancel, Escape, outside or other answers clear A10 and A11 and pause the game; other A items are preserved unless a separately specified nested operation changes them.
- L04 (direction or control press): modified Cmd, Ctrl or Alt keys are never held tokens; the game effect is a separate legal operation; A13 progresses only when a repeat starts under L06; the remaining items are preserved and a composition record is required.
- L05 (release): release-repeat timing is partial and was not guessed. Disconnect releases all tokens (INP4); the repeat consequence is in L06.
- L06 (repeat progression): the repeat phase advances and goes idle when paused, over or blurred; each repeat move or soft drop is nested; A12 does not become arbitrarily discardable from the phase rule.
- L07 (touch begin): the source has no automatic-pause input exception.
- L08 (touch update): committed moves are retained and no rollback is inferred (E1).
- L09 (touch end or cancel): A14 effect none; a rotation is nested only when the touch never went beyond 10 px and ends within 10 px, not for a cancel; the composite "hidden" relation in W32 and W33 (see their lines above) is open.
- L13 (lock): A3 is preserved, except for the later game-over semantic absence.
- L15 (pause or page hidden): D32 does not explicitly assign A14 for page-hidden, so a hidden reset needs a separate touch-cancel composition and not a silently added mask.
- L16 (resume): the representation of held-repeat suppression (D33 C3, D34 E2 and E3) is open; A12 tokens are not a new permission to discard; A13 stays idle and held-suppressed until release or a new press.
- L17 (Continue): a fresh bag only when the saved bag is missing; controls and cancel projection need separate sources; load is not to be treated as spawn reset permission.
- L18 (ordinary game over): A2, A3, A4, A6, A9, A14 and A15 lose semantic value and clearing is not required; A5 stays valid at 3 and A1 and A7 are retained unless preceding lock effects authorize otherwise.
- L19 (fault stop): the ordinary R1 and L18 semantic absence is not to be applied blindly to fault contents; a fault alone is not an A16 withdraw; ordinary contents are retained (F2) except the required safe changes.
- L20 (opening): the initial held-token contents need a source and physical-input relation and are not inferred empty; the row is not an ordinary D32 legal-action frame.
- L21 (persistence-only, read or event): such operations may change external, cache or presentation state without committing authority; A16 changes only S9 lifetime effects, and an accepted Continue may commit saved A items under L17.
- L10, L11, L12 and L14 carry only assignments and the pending-citation note, so nothing else is kept for them.

### Validation relation the paper proposed (not an implementation finding)

For each row: select the specified legal operation, an independent pre-state, the allowed write set, nested operations, the ordinary and fault commit, and the required checkpoints. Record concrete before and after snapshots by category and object identity, storage events, outstanding timer firings, focus, control and touch values, and reports. Verify that all unassigned A items are preserved under Z1 and the assigned values match D32, D33 and D34, not production's expected outputs. Original terse wording, meaning not clear from the paper alone: "Treat Undefined/supplied partial choices under current O8 preflight/trace-rejection limits." ("Undefined" is kept as written.) Failed cases are classified as requirement, model, representation or mapping error separately. An evidence count or method matrix alone cannot close Phase 3 or Phase 4. O1 and O7 remain Not Assessed (as stated October 5, 2026; the certification record's O1 to O8 table now lists each as Partially Established).
