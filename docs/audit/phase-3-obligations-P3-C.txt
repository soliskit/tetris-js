### Requirements PCE-1 to SCO-3: assumptions and limits as recorded

- PCE-1. Summary: In every committed non-fault state the board has exactly 20 rows of 10 cells, each empty or one of the seven kinds' colors; no operation puts anything outside it and a position outside holds nothing. Assumptions: the lock precondition (piece fits, see PCE-6); untrusted storage is validated (D23 U1). Limits: authoritative state only (SC:140-175 draws from gameManager.rows/columns). "Positions outside hold nothing" has no separate predicate in B5; it is carried by out-of-board reads giving nothing and by fits rejecting them. lockTetrominoInPlace writes before the post-operation check (allowed by V1, D16 section 6).
- PCE-2. Summary: Each kind's rotation states equal the adopted reference (four blocks each; 4 states, O 1), one fixed color per kind, seven pairwise distinct colors so color identifies kind. Assumptions: the two files are the oracle fixed by checksum (D18). Color values are not oracle-defined; the requirement gives none. Limits: image/table consistency unchecked (G6). The tests' own tables have unknown provenance. piece.color is a mutable field; "fixed" relies on no writer assigning it (none found in files read). Kick data is PCE-4, not PCE-2 (G2).
- PCE-3. Summary: Every newly current piece has rotation 0 at row 0, column 3 (I), 4 (O) or 3 (3-wide kinds), blocks in rows 0 to 1; if it does not fit the game ends (STA-3, not owned here). Assumptions: B2 geometry. Limits: G5. A 3-wide piece on 10 columns occupies columns 3 to 5 (tie goes left). The I piece's blocks sit in box row 1, so it appears in board row 1 only, which is inside "top two rows".
- PCE-4. Summary: Rotation tries the target direction's kicks in table order and takes the first fit; if none fits it tries the other direction; if none fits nothing changes; O never changes. Assumptions: the kick table is the SRS table the requirement names; an oracle must first be adopted. Limits: G2. A read of TF:28-42 against the usual SRS tables (converted to row-down coordinates) showed no difference by eye, which is not an oracle. A successful non-O rotation always changes the state, so the lock-delay reset runs only then (GM:587).
- PCE-5. Summary: (a) between refills each kind is dealt once per seven consecutive deals; (b) after New Game the first seven pieces dealt (current, three queued, three more) all differ; (c) Continue deals the saved remaining bag, or a fresh full bag when none was saved; (d) the random source is replaceable. Assumptions: D24 V3. Limits: no unpredictability claim (V3). An accepted save need not agree with whole-bag dealing (B15, S11), so (a) holds for play the game produces. The loader's array is given to the factory by reference (P2-A O-12). A random() value of 1, NaN or a negative value makes shuffle place undefined entries (TF:80-87), after which generate returns undefined; D24 V3 trusts the source, and whether to check it stays an evidence question.
- PCE-6. Summary: In every committed state with a current piece (playing or paused) the piece is on the board on empty positions; after an ordinary game over the retained overlapping piece has no semantic value (B6); committed states only, not microsteps (V1). Assumptions: V1; the prior committed state fits. Limits: the invariant monitor checks fit only while playing (GM:419), so a paused committed state is not covered by it. Hard drop and gravity assign positions without their own fit check and rely on the derived target. Unguarded public methods can be called directly (P2-A B1; O1/O7 partition).
- PLY-1. Summary: While playing, a move changes only the column by one when the target cells are on the board and empty; otherwise nothing changes and no lock-delay reset happens; nothing else changes except the lock-delay items B9.2 assigns (PLY-6). Assumptions: PCE-6 for the prior state. Limits: repeat timing and input semantics are INP partition. A move while paused or over is ignored by the mode check at GM:551 (STA-2 elsewhere).
- PLY-2. Summary: (a) every gravity request equals max(0.25, 0.7 - 0.02 x (level - 1)) x 1000 ms within 1e-9 ms for the level at the time of the request; (b) score, hence level, changes only in a lock, and each lock path restarts the timer afterwards, so a pending timer carries the current level's interval; (c) when it fires while playing the piece moves down one row unless it rests; (d) the timer is not running when not playing (STA-2/U4, SAF partition). Assumptions: D21 S10 scope; D22 T3; D23 U4. Limits: requested delay only (S10). Resume and Hold start a full new interval (GM:500, 579); elapsed time is not kept, and no source speaks to it. Pause/resume timer rules are STA/SAF.
- PLY-3. Summary: While playing, soft drop moves the piece one row down when the cell below is free, applies B9.2 for a new lowest row, and restarts the gravity timer at the current level's interval; a resting piece does not move. Assumptions: PLY-2 (a), the requested gravity delay; scheduler trust T3. Limits: the requirement is silent when the piece cannot move; the code restarts the timer then (GM:255). Soft drop awards no points (no SCO text says otherwise). softDrop clears the confirmation outside the guard (GM:527-529; P2-A B2); that is STA-1, not a P3-C property.
- PLY-4. Summary: While playing, the piece goes to the lowest free position straight down and locks at once (lock, full-row clear, next piece, possible game over); when lines are cleared and the game goes on the save captures the completed turn; if the turn ends the game no save is written (D33 C1). Assumptions: PCE-6 prior state; D33 C1. Limits: no points for drop distance (requirement silent). The high score write before the rest of the turn (GM:349) is STA/SAF O4.
- PLY-5. Summary: (a) engine: ghostTetromino's position equals B14's landing position; (b) display: the drawn ghost cells are those cells, drawn as outlines distinct from the piece. Assumptions: PCE-6 for the current piece. Limits: sub-claim (b) is Not Assessed: no browser evidence exists or was gathered (G7). The ghost also shows while paused; the requirement is silent. Board redraw depends on boardVersion bumps; whether the gating can miss a board change is Phase 4.
- PLY-6. Claim (B9.2): the delay starts when a piece comes to rest by any route; a move or rotation on a resting piece below count 15 that reaches no new lowest row adds 1 and restarts the delay; reaching a new lowest row sets the count to 0 without incrementing; at 15 a move or rotation does not restart the running delay; moving off a ledge cancels the delay (no count change is stated); at 15 a piece whose delay was cancelled and that rests again locks at once; a pause during the delay counts as one reset (14 or less: +1 and the delay restarts on resume; 15: becomes 16 and resume locks at once); 16 exists only paused and resting. Assumptions: D22 T3; B9.2; no decision yet on judging the 0.5 s delay (G4). Limits: six candidate observations to compare with the governing text, each needing reproduction before it counts as a finding. (1) Lowest row uses the box row (GM:300-310, 216), not the greatest occupied block row; compare D17 item 15, B9.1, B9.2, B16 L1. A rotation can change occupied rows without changing the box row. (2) A move or rotation reaching a new lowest row while the delay runs and the piece still rests: noteLowestRow sets count 0, then resetLockDelay adds 1, so the count ends at 1, not 0 (GM:294-296; B9.2 says it sets the count to 0 and does not increment). test/gameManager.test.js:973 accepts count <= 1. (3) Moving off a ledge while a delay runs adds 1 (GM:291-293); B9.2 states no count change for it. At count 15 this gives 16 in a playing state (B9.1 allows 16 only paused and resting). At 14 it makes 15, so a later landing locks at once (GM:280-281) where B9.2 would start the delay. test/gameManager.test.js:445 asserts the increment. (4) Resume with count 15 locks at once (GM:280-281); B9.2 says only 16 locks at once, and a pause that took 14 to 15 resumes with the delay. test/gameManager.test.js:631 sets 15 by hand before pausing (reaching 16), so the 14-to-15 case is not exercised. (5) Continue restores neither the reset count nor the lowest row (sets count 0 and the lowest row to the box row; GM:216, 306-310), and serializeSession omits both (SS:29-39); D18 B16 says Continue restores saved values (new saves) or applies L1/L2 (legacy); compare D17 section 3. Save format is STA/SAF. (6) The lock-delay callback has no mode check and keeps its handle after firing until a later cancel (GM:266-269; P2-A O-3, O-4); relevant to U3/U4 (SAF partition).
- PLY-7. Summary: While playing and available, Hold stores the current piece in spawn state, brings in the held piece (spawn state) or the next piece, makes Hold unavailable until the next lock cycle, and gives the brought-in piece a fresh count and lowest row. Assumptions: B8 reading of "once per piece". Limits: on the no-room held-piece branch the function returns before the held piece and hold-used are updated (GM:566-569); the no-held branch updates them even at game over (GM:577-578). B8 gives neither a semantic value at game over, so this is a representation difference to confirm in correspondence. Hold restarts gravity (GM:579). Remark (1) of PLY-6 applies to the brought-in piece.
- PLY-8. Summary: (a) engine: after every committed state the queue holds exactly three pieces, each a valid kind; (b) display: while playing or paused the three queued pieces are drawn in order in the three next boxes, and not at game over. Assumptions: PCE-5 for the dealt kinds. Limits: sub-claim (b) is Not Assessed: one e2e test, no visual verification here (G7). The preview cache is keyed by piece object identity (SC:310-317). The engine check covers the count only (GM:417). The element-validity reading of B7 is open.
- SCO-1. Summary: After a lock every completely filled row is removed, the remaining rows keep their order and move down by the number of removed rows below them, empty rows are added at the top, and the score rises by 100, 300, 500 or 800 for 1 to 4 rows. Assumptions: NF as an inductive invariant. Without it, five or more full rows would give LINE_SCORES[n] undefined and a NaN score (GM:348), which the score check would stop (GM:418). Limits: G3 (B15 does not require NF of the model, the loader enforces it, the monitor GM:412-428 does not check it). The high score write inside clearFullRows is SCO-3.
- SCO-2. Claim: For every score the engine can hold, level = floor(score/1000) + 1. Proof method (proposed): reviewed deductive argument that IEEE division of a safe integer by 1000 never rounds a non-multiple up to the next integer (the nearest fraction margin 0.001 exceeds the half-spacing of about 4.9e-4 at 2^53 [wording as in the paper; see the dated note below]; for multiples of 100 the margin is 0.1), plus boundary enumeration (0, 999, 1000, 1999, 2000, 2^53 - 1). Assumptions: score is a non-negative safe integer (GM:418, B11). Limits: the page does not show the level (no level element found in index.html or script.js); it reaches the player only through gravity speed (PLY-2). Scores above MAX_SAFE_INTEGER are rejected by GM:418 and SS:160 (B11 sets no format limit, B3). Both also require score % 100 = 0, stricter than B11 ("no divisibility condition"): scores in play are multiples of 100, but a B11-valid score such as 150 is rejected; cross-reference STA/SAF.
- SCO-3. Summary: (a) the engine's own writes never lower the stored value (each write stores max(valid stored value or 0, score)); (b) a stored value that is not a whole number >= 0 counts as 0 and is replaced by the first higher score; (c) the value persists across New Game and game over; (d) a failed write or read does not stop play. Assumptions: D23 U1. Limits: the writer stores max(...) even when the score is not higher, which rewrites the current value (possibly in canonical form); this is not a decrease. Number() accepts forms such as "1e3", "0x10", " 7 " (B3 says no numeric format limit is part of R1; whether these "denote exactly one value" is open, G9). Read and write are separate calls, so a lost update between two tabs is theoretically possible. The label follows a snapshot of mode, score, saved flag and confirmation (SC:319), so it can lag a change by another tab until the storage handler redraws (e2e/game.spec.js:400). Write ordering within the lock turn is STA/SAF O4.

The image `docs/sources/1-SRS-pieces.png` (SHA-256 5a5c49e378cf00a2632a4cd3b5af36d3831dbbdcc64f8d7b09b93c2353821236, equal to D18) was not compared; D18 B2 says a table and image disagreement stops for an owner decision, so the consistency check is an open Phase 3 step. SCO-2 is the only status marked Proven by Reviewed Argument in the certification record; the certification record points to this record for its argument. The paper labels that text a proposed proof method ("Proof Method (proposed)"), and its entry above is printed as written. A note added in this rewrite, dated October 25, 2026 (an annotation of the proposed argument, not a change to any status): the entry gives the half-spacing of doubles as about 4.9e-4 "at 2^53". The relevant size is the largest quotient, 2^53 / 1000, about 9.0e12, which lies between 2^43 and 2^44. Doubles there are spaced 2^-9 apart, so the half-spacing is 2^-10, about 9.8e-4. The stated margin of 0.001 still exceeds it, with about 2.4% headroom, and the same reasoning gets easier in lower ranges. A separate recomputation agrees with these figures; it checked only a sample, which is not a proof over the whole range. The recorded status is unchanged, and this rewrite does not endorse or re-derive the argument.

### Mapping gaps recorded with those requirements, labelled P3-C G1 to G10 (open at that stage; the writer-frame matrix has its own G1 to G10)

- P3-C G1. D25 section 2 omits or only partly covers PCE-2, PCE-5 (only O6), PLY-2, PLY-5, PLY-8 and SCO-3 (only O3); PCE-2, PLY-2, PLY-5 and PLY-8 are listed under no obligation. The records name the property actually used. A D25 correction or Phase 3 note is needed.
- P3-C G2. PCE-4 and PCE-2: no Phase 1 decision adopts an oracle for kick data (D18 B2: the geometry reference gives geometry only and wall-kick data is not part of it). Candidate sources are in Appendix C of the blueprint. Adoption is a Phase 1 decision, so it needs the audit's decision route and not a record edit.
- P3-C G3. D18 B15 does not make "no completely filled row" a validity condition, yet the loader rejects full rows (SS:92-93) and SCO-1's argument for n <= 4 relies on that invariant. The model accepts a saved board with full rows, the loader rejects it. The STA and SAF partition must settle persisted-validity correspondence.
- P3-C G4. PLY-6 0.5 s delay: no decision says it is judged on the requested delay, as D21 S10 does for PLY-2.
- P3-C G5. PCE-3 "centered": no tie rule for odd widths.
- P3-C G6. B2 table and image consistency check is open. The table lists O with four identical state rows, while B2 says O has one valid state.
- P3-C G7. The PLY-5 and PLY-8 display sub-claims have no browser or pixel evidence and no D25 row. Which partition owns preview and ghost display evidence needs confirming.
- P3-C G8. PLY-1, PLY-3, PLY-4, PLY-7 and PCE-4 input paths are cross-references to the INP partition. The INP mapping must confirm each reaches handleAction or softDrop.
- P3-C G9. SCO-3 stored-text forms accepted by Number() versus the B3, B11 and B16 wording; a Phase 1 reading may be needed.
- P3-C G10. Every model-transition field is pending the frozen O8 model (gravity tick, lock-delay automaton, hold, spawn, lock-with-clear).
