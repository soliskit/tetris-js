8. CANDIDATE OBSERVATIONS (not findings; no status; each needs comparison to governing text in Phase 3)
C1. Item 16 (D20, S9) has no code counterpart in the inventoried files. S4 (failed withdrawal: not offered in running session) and S9 describe session state; code has only the cached flag plus stored flag. If the withdraw write throws (:168-170), cache was cleared at :165 so the next read re-reads storage and may return the old "true".
C2. Continue success (:207-216) does not clear the flag or set any indicator. D20 provenance describes an owner choice "Continue withdraws the old save", but D21 S2 lists withdrawal only at New Game confirm and normal game over. Whether Continue is a withdrawal trigger is for the governing text to decide; code behavior stated here only.
C3. Failed read vs S7: readItem swallows read errors and returns null (:133-139). In loadGameSession a null saved-session read gives parseSession null (session.js:151-155), then W-b(false) at :204, i.e. a withdrawal write after a failed read. S7 says a failed read does not by itself withdraw and changes no stored value. The flag read R-a failing is cached as false without a write (:159).
C4. Failed save vs S5: saveGameSession catch (:223-225) calls W-b(false) (withdraws previous save), consistent in shape with S5. But the try block includes W-b(true) (:222): if the flag write itself threw inside the setter it is swallowed in the setter, so the catch is reached only by W-c or serializeSession throwing. Partial-failure state (saved bytes new, flag old value) possible when W-c succeeds and W-b(true) throws silently (:167-170).
C5. Write order in saveGameSession: bytes first then flag (:221-222). Flag-then-bytes interleaving by another tab is not tracked (S9 says no cross-tab tracking).
C6. Score/high-score ordering at line clear: highScore written (:349) before saveGameSession (:322 after lockAndSpawn). W-a failure swallowed (:151-153), no fault reported.
C7. holdTetromino game-over branch (:566-569) returns after stopGameLoop/cancelLockDelay without touching held/canHold; no save. Persistence effect is the flag withdrawal only.
C8. sw.js lists 'game/session.js' in its cache list (sw.js:37): static asset reference only, no storage. Handoff to P2-E.
C9. parseSession accepts saves with no bag key (session.js:176-178 returns empty bag; resetBag(session.bag) at gameManager.js:215 then receives []). Whether resetBag([]) means "fresh full bag" depends on tetrominoFactory (not read by me; hand-off to P2-A).
C10. saveGameSession writes the session while paused with lockDelayResetCount/lowestRow adjusted (:490-493), but serializeSession (session.js:29-40) does not include lock-delay reset count or lowest-row; loadGameSession recomputes via resetLockDelayForNewPiece (:216, :306-310). D32 Continue row says items 1-9 and 15 restored exactly as saved. Candidate comparison for Phase 3 against D16 items 9 and 15 (which items the saved game must contain is stated by R1 B16, not read in full by me).
