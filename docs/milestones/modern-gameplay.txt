Modern Gameplay

Seven gameplay changes, delivered in a fixed order with the rules and evidence updated together.

Status
Planning is complete. Implementation waits for the audit program and CI Pipeline Optimization to finish,
then a separate go-ahead. This plan starts neither program and changes no current gameplay requirement.
The direction is a modern Guideline-style feel: faster gravity, drop points, T-spins, combos and short
delays. This is not a claim of full Guideline compliance. The values below are proposed stage defaults,
not final requirements or verified external facts. Each stage needs exact reviewed requirements before
implementation. Existing high scores stay unless evidence exposes a material product-direction conflict.

Order and scope
1. Rotation direction
2. Gravity
3. Scoring
4. Level progression
5. T-spins and combos
6. Entry and line-clear delays
7. Hidden rows
Back-to-back bonuses, perfect clears, start-level selection and game completion are outside this plan.
Finish one stage before implementing the next. Adjacent stages may form one release only with separate
approval. Scoring and level progression are the first proposed pair, not an approved release group.
An approved group keeps the stage order, ships no intermediate stage and is certified as one candidate.

1. Rotation direction
Try only the requested direction's SRS wall kicks, in order. If none fits, leave the piece unchanged;
never try the opposite direction. The O piece does not rotate. Replace the old fallback protections with
a check that proves the opposite direction is not tried. No save-format change is expected.
Use a fixed, checksummed SRS reference before building the independent model: one kick table for J, L,
S, T and Z, one for I, none for O. Geometry alone does not supply kick data. Reuse an adopted fixed
reference if available. Whether the current derived counterclockwise kicks match the reference remains
unverified; report a difference rather than silently changing the reference to match the code.

2. Gravity
Proposed seconds per row: max((0.8 - 0.007 × (level - 1)) to the power (level - 1), 1/60).
The curve applies through level 13; the 1/60-second floor applies from level 14, with no level cap.
The floor is a project choice, not a browser timer minimum or 20G. Gravity still moves one row at a time.
The interval is the requested scheduler delay, not a promise about measured fall rate.
Soft drop stays one row per press, then every 50 ms. A successful soft drop restarts gravity; natural
gravity continues between repeats. At high levels, holding soft drop need not produce a faster observed
fall rate. This stage adds neither multi-row falls nor elapsed-time clock reads. No save change is expected.

3. Scoring
Award 100, 300, 500 or 800 points for one, two, three or four cleared lines, multiplied by the level
before the clear. Add one point per soft-drop cell and two per hard-drop cell. T-spin and combo awards
arrive in stage 5. Keep the device high score and replace it only with a higher score.
Scores are non-negative safe integers. Every award saturates at the largest safe integer; loading and
runtime checks use the same bound. Recheck all score-domain protections, including historical
multiple-of-100 checks, and replace any affected protection consistently rather than just removing it.
Scoring actions gain explicit score effects in the state-transition rules.
The current score-derived level would feed back into later awards. Release stages 3 and 4 together only
if their group is approved. If released separately, the scoring-only feedback rule needs explicit approval
and certification. Older-version score and save compatibility stays unverified until the new domain is set.

4. Level progression
Start at level 1 and gain a level every ten cleared lines, with no level cap. Store total cleared lines as
an authoritative value with the same safe-integer bound as score; level no longer comes from score.
For a legacy save, derive its old level from score, then default cleared lines to (old level - 1) × 10.
That is a default, not recovered history. Continue to ignore the legacy stored level unless the
compatibility requirement changes. If the new rule cannot represent an old level, return the fallback
for a product decision with evidence. A new save format is likely, not yet established as necessary.

5. T-spins and combos
On lock, recognize a T-spin when the T's last successful maneuver was a rotation and at least three of
its four diagonal center corners are occupied. Board edges and the floor count as occupied. It is a Mini
when only one front corner is occupied, unless the last rotation used the 1-by-2 kick, which makes it full.

Multiply awards by the level before the clear: Mini with no lines 100; full T-spin with no lines 400;
Mini single 200; full single 800; Mini double 400; full double 1200; full triple 1600.
Each consecutive line-clearing lock adds 50 × combo count × level; the first clear has count 0.
A lock with no clear resets the chain. A T-spin with no clear does not continue it.
Keep the last-rotation and 1-by-2-kick history needed for recognition; reset it on a new piece or Hold.
The combo count carries across pieces and Hold and resets only on a lock without a clear. Persist all
history needed for exact Continue restoration, including the combo count. Define recognition first,
then state and validation. A save-format change is likely if new state is persisted.

6. Entry and line-clear delays
Start with a fixed 0.4-second line-clear delay and 0.1-second entry delay. These are unsourced proposed
values, not established Guideline requirements. Later changes are gameplay-requirement changes, not
private tuning. Distinguish falling, line-clear delay and entry delay independently of timer handles.
Save a line-clearing turn only after the delayed transition finishes with the next piece in place.
If the turn ends the game, write no save. Pause completes a pending transition, then pauses: it does not
persist the delay phase or require a new format for this stage. During either delay, ignore movement,
rotation, Hold and drops; Pause and New Game still work. Do not buffer inputs for the next piece.
Repeating controls need release and a new press after a delay, as after resume. Touch behavior stays intact.
While falling, gravity runs and lock delay runs exactly while resting; delay timers do not run.
During a delay, only its delay timer runs. Paused and game-over states run no covered gameplay timer,
subject to existing cancellation-failure stopping rules. Check invariants after every action and covered
timer; broken invariants still invoke safe stopping, and legal play must preserve validity.
Extend timer registration, cancellation, failure and timing rules to delay timers. Reassess lock and
completion transitions, every affected state assignment, save boundaries, controls, ghost/preview and
error display. Reassess idle redraws if wakeups change. Clock-jump duties apply if elapsed time decides state.

7. Hidden rows
Add two hidden rows above the visible 10-by-20 board. Pieces spawn there and fall into view; kicks may
move a falling piece there. Do not draw hidden rows. If any cell locks in a hidden row, end the game
without a save. If a new or held piece cannot spawn, end the game. No locked cell remains in a hidden row.
This is deliberately smaller than the commonly described 20-row buffer and stricter than whole-piece
hidden lock-out; the reference informs the design without making this full Guideline compliance.
Keep the saved locked board 10 by 20, without padding. A paused falling piece may occupy the hidden
rows, so its valid saved position extends upward by two rows. Reassess spawn, fit, lowest-row history,
ghost, lock delay, touch, drawing and failure rules. Determine whether the widened semantic domain needs
a new format or causes older-version incompatibility; do not assume either a taller saved board or a
validation-only change before that analysis.

Evidence and compatibility
Before each stage, check the current tree and affected rules. Define exact behavior, state, timing,
saving and compatibility without using implementation output as the specification. Independently review
the same exact requirements before within-plan approval and implementation; reviewer and approver are
distinct. Freeze their identity and a clean model input pack before comparison. Prefer a fresh model
author; reuse needs the existing post-freeze rules and a written owner-approved independence exception
addressing prior implementation exposure.
The model receives requirements and fixed references, not code, tests, outputs, traces, derived fixtures,
prior correspondence or implementation findings.
Freeze and checksum the model before comparison; disagreement alone never justifies changing its rules.
Keep unaffected protections and QA-1 through QA-6. Cover transitions, malformed states, persistence,
timers, trust boundaries, display and compatibility at their affected scope. Report assumptions and limits,
including mutation survivors, errors, timeouts and exclusions. Green tests, a model match or a nominal
100% mutation score alone do not establish certification. Do not narrow coverage, browsers, mutation,
falsification or trust boundaries, add masking retries, bypass gates or remove protections without approval.
New save formats need an explicit validated version, validated defaults or migration, and exact Continue
semantics. Do not invent a format for convenience or describe defaults as recovered history. Preserve
required legacy support. Do not claim a format unchanged when exact restoration needs new information.
If an older live version is incompatible, use a new game-owned storage name;
define eligible reads, precedence, withdrawal, Continue availability and ownership. No unnecessary split
is required for a compatible format. Build a fixture from the frozen candidate serializer before merge,
run migration/compatibility checks, then confirm the deployed serializer's identity after deployment.
A candidate fixture alone is not evidence from a released version.
Certify the exact candidate before merge and release, with a complete checksummed code-to-claim inventory,
methods, assumptions and limits. A changed requirement stops dependent work for impact review and renewed
approval; affected model semantics need a new clean frozen model. A merge change needs affected evidence
refreshed. Confirm the merged content, required main checks and deployed identity before closing release.

Boundaries
Within-plan engineering and exact stage details remain delegated after independent review. Changes to
scope, product direction or governing requirements, safeguards, trusted boundaries, costs, settings, checks or
charter-level save/compatibility and certification policy need separate approval. Adjacent release groups
also need approval. Merge, release and deployment decisions remain with the repository owner unless a
separate scoped permission is granted. This plan grants none and starts no implementation.
